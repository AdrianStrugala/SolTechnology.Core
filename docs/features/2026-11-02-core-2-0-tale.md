# SolTechnology.Core 2.0 — Tale

> Historical delivery record. It may not describe the current system.

## Goal

Deliver the 2.0 hardening of `SolTechnology.Core.Tale` end-to-end, as one library of the SolTechnology.Core 2.0
flagship release. Success means:

- Tale errors keep their types in persistence through a public, read-only `TaleJsonOptions.Default` (`C-26`, Tale half of `B7`).
- Each run has isolated state, and only `TaleManager`-driven runs are persisted (`B8`, P-02); the engine honours caller-only cancellation and never resumes a failed tale.
- The 2.0 contract is deliberate: chapters take a `CancellationToken`, `ITaleRepository` has cancellable, suffix-free methods with optimistic concurrency, history is keyed by step index and version-free type name, and HTTP exposure is opt-in (`C-03`…`C-07`, P-03, P-04, P-12).
- Tale ships XML docs, a `docs/Tale.md` README that compiles against 2.0, conforms to the Coding Guide, and logs with `[{Placeholder}]` templates.

## Post-completion review fixes (2026-11-03)

An independent code review of the completed feature found four issues, and the user decided a
fifth (T5); the fixes are on `master`. Every listed test failed before its fix and passes after.

- **T1 — finding:** `TaleHandler.Run.cs` persisted `TerminalStatus` without recording why the run
  ended. A token cancelled between two saves (inside a repository call, not a chapter) stored the
  last chapter's outcome, usually `Completed`; an exception outside a chapter (an inline `Do` step)
  stored `Completed` too. **Fix:** the cancellation catch calls the engine's internal
  `MarkCancelled()` and the generic catch calls `Fail(error)` (`TaleRunState.Fail(null, error)`)
  before the terminal save. **Tests:** `TaleTerminalStatusTests.Start_TokenCancelledDuringSecondSave_StoresCancelled`
  (stored `Completed`) and `Start_InlineStepThrows_StoresFailed` (`GatedTaleRepository`).
- **T2 — finding:** `TaleEngine.ReadChapter` and `TaleHandler.Run` returned `Error.From(ex)`, so
  the exception message reached the HTTP start/resume body and the persisted `ChapterInfo.Error`
  served by `GET /api/tale/{id}`. **Fix:** both log the exception once (bracketed template) and use
  the new internal `UnexpectedFailure.Of(...)`: "Chapter [X] failed unexpectedly." or "Tale [X]
  failed unexpectedly.", with the `Activity.Current` trace ID as `CorrelationId`. **Tests:**
  `TaleControllerTests.Start_ChapterThrows_NeitherStartBodyNorStoredStateContainExceptionMessage`
  and the message assertion in `Start_InlineStepThrows_StoresFailed`. Four existing tests that
  pinned the exception text (`ErrorHandling_ShouldConvertException_ToError`,
  `Chapter_HttpTimeout_IsChapterErrorNotCancellation`, `TaleEngine_ShouldConvertExceptions_ToErrors`,
  `Repository_SaveFailure_ShouldPropagateError`) now assert the generic message.
- **T3 — finding:** `TaleController.GetStoryState` and `CancelStory` served any stored tale, so a
  client could read or cancel a tale of a handler not opted in with `ExposeOverHttp`. **Fix:** both
  load the tale through `FindExposedTale`, which turns a tale whose `HandlerTypeName` the registry
  does not resolve into the same "Tale not found" 404 as a missing tale; `CancelStory` therefore
  answers a missing tale with 404 instead of 400. **Tests:** `GetState_NonExposedHandlerTale_Returns404`
  (body equals the missing-tale body) and `Cancel_NonExposedHandlerTale_Returns404AndDoesNotCancel`.
- **T4 — finding:** `InteractiveChapterInvoker` called `ReadWithInput` with `MethodInfo.Invoke`, so
  a non-async chapter that threw synchronously surfaced as `TargetInvocationException`: a caller
  cancellation stored `Failed`, and the chapter error was logged with the wrapper. **Fix:**

#### Imagined Failure

registered `Scoped`, as `docs/Tale.md` shows, reports customers charged twice. Their repository

the heartbeat keeps refreshing `LastUpdatedAt` for a chapter that has hung on a retry-forever
policy since Friday, and `ResumeStory` answers "Tale is already running" for it every time.

**Go with mitigations** — no `H` scenario lacks a plausible mitigation, but scenarios 1, 2 and 8
need code fixes before 2.0 ships. Two decisions belong to the user and do not block those fixes:

- **D1 — lease storage:** keep measuring the lease from `LastUpdatedAt` with the same timeout
  documented for every host, or persist the lease explicitly (for example a writer-stamped
  `TaleInstance.LeaseExpiresAt`), which is a persisted-contract change every custom repository
  must migrate and would need its own premortem.
- **D2 — bounding a live run:** keep `CancelStory` plus the long-step warning as the only recovery
  for a hung but alive chapter, or add a public `TaleOptions` limit after which the heartbeat stops
  renewing so the tale becomes resumable.

#### Imagined Failure

Two months after 2.0.0, a consumer that upgraded its Dapper repository by adding the `Version`
column (the compile break and the migration guide made that obvious) reports duplicated shipments.
Their `UPDATE` lists columns by hand and never got `LeaseExpiresAt`, so every row reads it back as
`null`; the library treats `null` as an expired lease, and the mobile client's automatic retry of
`ResumeStory` takes over every live run within milliseconds and re-runs the shipping chapter in
parallel. Nothing logged an error: the takeover warning reads like a normal crash recovery. A second
consumer stores the value in a `datetime2` column and converts it back with the implicit
`DateTime`→`DateTimeOffset` conversion; their CI and Azure containers run in UTC and pass, but the
on-premises plant in Kraków (UTC+1) sees every lease one hour early, which with the 5-minute default
means always expired.

#### Top 3 Risks

1. Scenario 1 — a repository that silently drops the new column turns every `Running` tale into an
   immediate takeover target: double execution with no error anywhere.
2. Scenario 2 — a repository that stores the expiry only on insert keeps the first lease forever,
   so resumed and long-running tales are takeable while alive, and the `null` fallback cannot see it.
3. Scenario 3 — an expiry rebuilt from a `DateTime` column is shifted by the host's time zone,
   invisible on UTC CI and fatal on UTC+N hosts.

#### Accepted Risks

- Scenario 4 — mixed pre-release builds on one store: no public consumer has a 2.0 build; drain
  pre-release hosts between builds.
- Scenario 6 — SQLite `ALTER TABLE` start-up race in the sample: the next construction succeeds and
  the same race already existed for `Version`.
- Scenarios 5, 7 and 8 — defended by existing controls.
- No public repository conformance test kit: the self-check is the runtime substitute; a reusable
  kit needs a new package (decision D5).

#### Decision

**Go with mitigations** — the two `H` paths with `M`/`L` likelihood (a dropped or stale expiry)
have plausible library-side mitigations without public API; the semver classification matches.
Decisions for the user, not blocking T8:

- **D3 — `null` expiry:** scenario 1's fallback changes the T7 rule "a missing expiry counts as
  expired" (recorded under D1). Recommended: fall back to `LastUpdatedAt`. If the user keeps
  `null` = expired, the D4 self-check must fail the run instead of logging.
- **D4 — self-check mode:** log an error and keep running (recommended), or fail the run with a
  repository-contract error when the read-back differs.
- **D5 — conformance kit:** whether to ship a reusable `ITaleRepository` contract test base for
  custom repositories; a new `src/SolTechnology.Core.Tale.Testing` package needs confirmation
  under `CLAUDE.md` §2.
