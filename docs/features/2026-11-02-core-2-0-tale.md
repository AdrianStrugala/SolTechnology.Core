# SolTechnology.Core 2.0 — Tale

> Historical delivery record. It may not describe the current system.

## Goal

Deliver the 2.0 hardening of `SolTechnology.Core.Tale` end-to-end, as one library of the SolTechnology.Core 2.0
flagship release. Success means:

- Tale errors keep their types in persistence through a public, read-only `TaleJsonOptions.Default` (`C-26`, Tale half of `B7`).
- Each run has isolated state, and only `TaleManager`-driven runs are persisted (`B8`, P-02); the engine honours caller-only cancellation and never resumes a failed tale.
- The 2.0 contract is deliberate: chapters take a `CancellationToken`, `ITaleRepository` has cancellable, suffix-free methods with optimistic concurrency, history is keyed by step index and version-free type name, and HTTP exposure is opt-in (`C-03`…`C-07`, P-03, P-04, P-12).
- Tale ships XML docs, a `docs/Tale.md` README that compiles against 2.0, conforms to the Coding Guide, and logs with `[{Placeholder}]` templates.

## Post-completion review fixes (2026-11-03)

An independent code review of the completed feature found four issues, and the user decided a
fifth (T5); the fixes are on `master`. Every listed test failed before its fix and passes after.

- **T1 — finding:** `TaleHandler.Run.cs` persisted `TerminalStatus` without recording why the run
  ended. A token cancelled between two saves (inside a repository call, not a chapter) stored the
  last chapter's outcome, usually `Completed`; an exception outside a chapter (an inline `Do` step)
  stored `Completed` too. **Fix:** the cancellation catch calls the engine's internal
  `MarkCancelled()` and the generic catch calls `Fail(error)` (`TaleRunState.Fail(null, error)`)
  before the terminal save. **Tests:** `TaleTerminalStatusTests.Start_TokenCancelledDuringSecondSave_StoresCancelled`
  (stored `Completed`) and `Start_InlineStepThrows_StoresFailed` (`GatedTaleRepository`).
- **T2 — finding:** `TaleEngine.ReadChapter` and `TaleHandler.Run` returned `Error.From(ex)`, so
  the exception message reached the HTTP start/resume body and the persisted `ChapterInfo.Error`
  served by `GET /api/tale/{id}`. **Fix:** both log the exception once (bracketed template) and use
  the new internal `UnexpectedFailure.Of(...)`: "Chapter [X] failed unexpectedly." or "Tale [X]
  failed unexpectedly.", with the `Activity.Current` trace ID as `CorrelationId`. **Tests:**
  `TaleControllerTests.Start_ChapterThrows_NeitherStartBodyNorStoredStateContainExceptionMessage`
  and the message assertion in `Start_InlineStepThrows_StoresFailed`. Four existing tests that
  pinned the exception text (`ErrorHandling_ShouldConvertException_ToError`,
  `Chapter_HttpTimeout_IsChapterErrorNotCancellation`, `TaleEngine_ShouldConvertExceptions_ToErrors`,
  `Repository_SaveFailure_ShouldPropagateError`) now assert the generic message.
- **T3 — finding:** `TaleController.GetStoryState` and `CancelStory` served any stored tale, so a
  client could read or cancel a tale of a handler not opted in with `ExposeOverHttp`. **Fix:** both
  load the tale through `FindExposedTale`, which turns a tale whose `HandlerTypeName` the registry
  does not resolve into the same "Tale not found" 404 as a missing tale; `CancelStory` therefore
  answers a missing tale with 404 instead of 400. **Tests:** `GetState_NonExposedHandlerTale_Returns404`
  (body equals the missing-tale body) and `Cancel_NonExposedHandlerTale_Returns404AndDoesNotCancel`.
- **T4 — finding:** `InteractiveChapterInvoker` called `ReadWithInput` with `MethodInfo.Invoke`, so
  a non-async chapter that threw synchronously surfaced as `TargetInvocationException`: a caller
  cancellation stored `Failed`, and the chapter error was logged with the wrapper. **Fix:**
  `BindingFlags.DoNotWrapExceptions`. **Tests:** `InteractiveChapterInvokerTests.Resume_ReadWithInputThrowsCancellationSynchronously_StoresCancelled`
  and `Resume_ReadWithInputThrowsSynchronously_LogsTheChapterException`.
- **T5 — user decision (2026-11-03), running lease:** a tale left `Running` by a crashed host could
  never be resumed. **Fix:** `TaleOptions.RunningLeaseTimeout` (new, default 5 minutes, setter
  throws `ArgumentOutOfRangeException` unless positive). `ResumableTaleLoader` refuses a `Running`
  tale whose `LastUpdatedAt` is younger than the timeout (`ConflictError` "Tale is already
  running", as before) and otherwise lets the resume take it over through the normal versioned
  claim, logging a warning. The clock is the injected `TimeProvider`. **Tests:**
  `TaleRunningLeaseTests.Resume_RunningAfterLease_TakesOverAndCompletes`,
  `Resume_TwoConcurrentTakeovers_ExactlyOneSucceeds` and `RunningLeaseTimeout_NotPositive_Throws(0/-1)`
  failed before; `Resume_RunningWithinLease_ReturnsConflict` passed before and pins the default.
  The tests use `FakeTimeProvider` (`Microsoft.Extensions.TimeProvider.Testing`, already in
  `Directory.Packages.props`). `docs/Tale.md` gained "Running tales and the lease" (chapters with
  side effects must be idempotent); `docs/architecture/tale-framework.md` describes the lease.
  **Deviation:** the lease reuses the existing `TaleInstance.LastUpdatedAt`, which every save
  already stamps from the run's clock and every repository already stores (DreamTravel's SQLite
  column is `NOT NULL` and round-trips UTC), so there is no new property, column or migration and
  `SQLiteTaleRepository`/`InMemoryTaleRepository` are unchanged. `LastUpdatedAt` cannot be missing
  from rows written by 1.x or 2.x; a hand-written JSON row without it deserializes to the read time
  (the property's initializer), so such a row becomes resumable one lease later rather than at
  once.
- **T6 — user decision (2026-11-03), lease heartbeat:** with T5 alone, a chapter that ran longer
  than `RunningLeaseTimeout` could be taken over while its host was alive. **Fix:** the internal
  `TaleLeaseHeartbeat` renews the lease on a `TimeProvider` timer every third of the timeout while a
  persisted run executes its steps, re-saving a frozen copy of the last stored `Running` state with
  a fresh `LastUpdatedAt` through the normal conditional `Save`. `TaleStatePersistence` makes saves
  and renewals take turns on one gate, so each uses the version the previous one stored. A renewal
  that meets `ConflictError` logs a warning, cancels the chapter's token (linked to the caller's),
  and stops every later save, so the run returns `ConflictError` and leaves the new owner's state
  untouched. Direct runs create no timer. **Tests:** `TaleLeaseHeartbeatTests.StartStory_ChapterOutlivesLease_RenewsLeaseAndRefusesTakeover`,
  `StartStory_AfterChapterEnds_StopsRenewingLease` (counts saves and live timers) and
  `StartStory_AnotherRunTookOver_StopsWithConflictAndKeepsNewOwnersState` failed before;
  `Handle_DirectRun_NeverRenewsLease` passed before and guards direct runs. They drive
  `FakeTimeProvider` (through the test-only `TimerCountingTimeProvider`) and wait on save signals
  from `GatedTaleRepository`'s new `AfterSave` hook. **Deviations:** chapter reading moved from
  `TaleEngine` into the internal `ChapterReader` to keep the engine under the 150-line cap; the
  heartbeat runs for the whole step walk, not only inside chapters, so long inline steps are
  covered; a beat during a slow renewal queues at most one more renewal instead of being dropped.
  `TaleOptions.RunningLeaseTimeout` and the `Chapter`/`IChapter` token docs were updated; no public
  API was added.
