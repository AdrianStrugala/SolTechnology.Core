# SolTechnology.Core 2.0 — SQL

> Historical delivery record. It may not describe the current system.

## Goal

Deliver the 2.0 hardening of `SolTechnology.Core.SQL` end-to-end, as one library of the SolTechnology.Core 2.0
flagship release. Success means:

- `IUnitOfWork` exposes `Begin` and extends `IDisposable`, so the DI-resolved contract is usable (`B3`, `C-15`, A4).
- Connection retry covers transient errors only, error translation is safer, and options are validated (RM-13).
- `SQLConnectionFactory` and `UnitOfWork` are internal, and DACPAC deployment blocks on possible data loss by default and logs through `ILogger` (`C-16`, `C-17`, L-04).
- SQL ships XML docs, a `docs/SQL.md` README that compiles against 2.0, and conforms to the Coding Guide.

## Deviations

### Shared SQL Server fixture for the test project (step 02)

**Original plan:** the tests use `SQLFixture` through the new `SQL.Testing` reference; steps 03 and 04 reuse it.

**Actual implementation:** `SQLTestEnvironment`, a `[SetUpFixture]`, starts one `SQLFixture` on first use, provisions a
`dbo.Items` table with a unique `Name`, and disposes it after the run, so tests that need no database never start a
container.

### Tests and the P-23 row (step 03)

**Original plan:** three tests (login failure without retry, translator description, empty connection string) and a
`P-nn` row for the validation and retry change.

**Actual implementation:** `SqlException` has no public constructor, so the translator test inserts a duplicate row into
the shared database; the host-start test also covers whitespace, and a fourth test pins `AddSolSQL(null)`. The row is
`P-23`, because the planned Redis reconnect feature had reserved `P-21` and `P-22`, and it also names the
`ArgumentNullException` and the fixed `Error.Description` texts. The code review later replaced the hand-picked retry
list and the translation of unknown numbers (see the last section).

### Safe DACPAC defaults also stop recreating the database (step 04)

**Original plan:** default `BlockOnPossibleDataLoss = true`; the other 1.x options were not mentioned.

**Actual implementation:** without `deployOptions` the deployer uses `new DacDeployOptions { BlockOnPossibleDataLoss = true }`,
so `CreateNewDatabase` and `DropObjectsNotInSource` keep their DacFx default `false`. The 1.x `CreateNewDatabase = true`
dropped and recreated an existing database on every deploy. An existing database is now upgraded in place, so
DreamTravel's persistent Aspire SQL container keeps its data across restarts.

### Real dacpac tests, run serially (step 04)

**Original plan:** `DeployDacpac_DataLossChange_IsBlockedByDefault` with `SQLFixture` and a test dacpac, or a unit test
of the default options.

**Actual implementation:** two tests deploy a dacpac built in memory through the DacFx `TSqlModel` API to their own
database on the shared server; the second pins the data-loss override and the L-04 templates. Under amd64 emulation on
arm64 each deploy spends about 2.5 minutes in target-model extraction, and running both in parallel failed, so they run
serially. The parallel failures exposed the missing `Microsoft.Identity.Client` assembly, which the code review fixed
after the user's dependency decision.

### One explicit binding snippet and the snippet build (step 06)

**Original plan:** remove the binding examples; compile every C# block in a throwaway console project.

**Actual implementation:** the unsupported `Configuration:Sql` auto-binding and the parameterless `AddSQL()` are gone,
but one `appsettings.json` section and an explicit `GetSection("Sql").Get<SQLConfiguration>()` stay, as
`PublicDocumentationGuide.md` and Guide §14 ask. The 7 C# blocks were built in an uncommitted web project (with Dapper
and EF Core SQL Server) with 0 errors and 0 warnings, so no snippet is marked illustrative.

### Conformance scope, template check, and API diff (step 07)

**Original plan:** `extension` blocks, braces, and comments across the library; the `grep` template check; an empty
public API diff.

**Actual implementation:** steps 03 and 04 had already braced every `if`, so only the two extension classes and three
comments changed. BSD `grep` misses unbracketed templates, so a `perl` check also ran and printed nothing.
`Microsoft.DotNet.ApiCompat.Tool` found no breaking change; strict mode lists only the compiler-generated `extension`
marker types.

Two choices differ from the review's wording:

- `Complete_AfterAwait_Commits` resumes on a new thread instead of after `await Task.Yield()`. NUnit runs async tests on
  a synchronization context, so `Task.Yield()` resumed on the same thread, and the test also passed against a scope
  without `TransactionScopeAsyncFlowOption.Enabled`.
- `SQLConnectionFactory` has explicit constructors instead of a primary constructor (Guide §9.5): the retry-delay
  constructor must be `internal` so DI never sees it, and a primary constructor is always as visible as the type.
