# SolTechnology.Core 2.0 — Cache

> Historical delivery record. It may not describe the current system.

## Goal

Deliver the 2.0 hardening of `SolTechnology.Core.Cache` end-to-end, as one library of the SolTechnology.Core 2.0
flagship release. Success means:

- The local cache evicts faulted entries, runs one factory per key (single flight), and the local lock is correct.
- Keys are namespaced by `TKey`/`TItem` without assembly versions, `DistributedCacheConfiguration.InstanceName` has no default and is validated non-empty at start, and options are validated (P-07, RM-2, RM-3).
- Lock and idempotency contracts drop the `Async` suffix (`C-13`).
- Cache ships XML docs, a `docs/Cache.md` README that compiles against 2.0, conforms to the Coding Guide, and logs with `[{Placeholder}]` templates.

## Deviations

### Resolution tests and the test project (step 01)

**Original plan:** dummy connection strings are enough, because resolution must not open connections.

**Actual implementation:** resolving `IConnectionMultiplexer` starts a connection attempt, so the test used
`abortConnect=false` until code review fix 1 made the installer force it; the connection string now has only a short
`connectTimeout`. The local and distributed sets are separate tests because both register the same lock and
idempotency interfaces. `Cache.Tests` moved to `Microsoft.NET.Sdk.Web` instead of adding DI and logging packages.

### Lock entries instead of semaphores (step 02)

**Original plan:** keep the per-key `SemaphoreSlim`, add a release guard and a per-entry deadline.

**Actual implementation:** acquisition never waits, so a semaphore added nothing; the service keeps one holder object
per name with a `TimeProvider` deadline, claimed with `TryAdd`, taken over with `TryUpdate` once expired, and removed by
reference on release. The dead whitespace-key checks in `ScopedCache` and `RedisCache`, which step 02 did not list,
stayed until code review fix 4.

### Key helper, validation scope, and shared multiplexer (step 03)

**Original plan:** a version-free type-name prefix, `InstanceName`/`ConnectionString`/local `ExpirationSeconds`
validation, the multiplexer factory set inside `AddStackExchangeRedisCache`, and DreamTravel `appsettings*.json` edits.

**Actual implementation:** `CacheKey` copies Tale's `ChapterTypeName` naming, because Cache cannot reference Tale;
`ScopedCache` keeps its JSON key, since one instance serves one type pair. The distributed `ExpirationSeconds` is
validated too, and a partial local configuration fails at start (P-20). The factory is set through
`Configure<IServiceProvider>` on `RedisCacheOptions`, so the multiplexer is still created on first use. Redis tests live
under a namespace-level `[SetUpFixture]` so unit tests start no container. DreamTravel uses only the local cache, so no
`appsettings*.json` changed.

### Rename reach (step 04)

**Original plan:** a pure rename in the two interfaces, four implementations, and Api/Hangfire call sites.

**Actual implementation:** Api and Hangfire had no call site; `<see cref>` tags and test method names that began with
an old member name were renamed too, because the acceptance grep covers `tests`.

### Page rewritten to the canonical structure (step 06)

**Original plan:** replace the 1.x method names and add the `InstanceName`, expiry, `C-13`, and RM-2 notes.

**Actual implementation:** nearly every section needed 2.0 changes, so `docs/Cache.md` was rewritten to the
`PublicDocumentationGuide.md` structure (295 lines, down from 430). All 10 C# blocks compiled in a throwaway project in
the git-excluded `.scratch/`, after one `CS8619` fix in the idempotency recipe.

### Braces outside the listed files (step 07)

**Original plan:** primary constructors in four services and an `extension` block in `RedisHealthCheckExtensions.cs`.

**Actual implementation:** as planned, plus braces for single-line bodies in `RedisIdempotencyStore`, and in
`ScopedCache` and `RedisCache` through a separate `chore(cache)` commit. The public surface differed only by the marker
types every C# 14 `extension` block emits.

### Template check and pinning tests (step 08)

**Original plan:** a `grep -rnE` check for unbracketed placeholders; update the log-asserting tests.

**Actual implementation:** BSD `grep` did not match the old templates either, so a `perl` check ran instead (13 hits
before, none after). No test asserted templates, so three new tests pin every template, level, and property value.
The local lock test forced its Warning with an overflowing `TimeSpan.MaxValue` expiry; code review fix 2 made that
value an argument error, so the test now gets the Warning from a failing clock.

**Actual implementation:** as planned, plus the whole `SolTechnology.Core.slnx` suite and a Release pack into the
git-excluded `.scratch/`. The architecture page is new, as planned; no other `docs/architecture/` page describes Cache.

## Follow-ups

  (5 seconds by default; `IRedisCache.GetOrAdd` waits twice) before it fails open. A fail-fast backlog policy or

## Code review fixes (2026-11-04)

An independent code review of `d9552f6b..2c833dc1` found four issues. Each behavioural fix has a test that failed
before the fix and passes after it. Before each code commit `dotnet build SolTechnology.Core.slnx` reported 0 errors
and `dotnet test SolTechnology.Core.slnx` passed 18 projects.

1. **Major — Redis down at start threw instead of failing open.**
   **Finding:** `AddSolDistributedCache` created the shared multiplexer with `ConnectionMultiplexer.Connect(connectionString)`,
   where `abortConnect` defaults to `true` for non-Azure endpoints. Since `IDistributedCache` uses that multiplexer
   through `ConnectionMultiplexerFactory`, Redis down at start made every `IRedisCache.GetOrAdd` retry a blocking
   connect, and the lock, the idempotency store, and the health check threw on resolution, against the fail-open
   promise of `docs/Cache.md`.
   **Fix (`943540f9`, trimmed by `20d97693` to stay within 150 lines):** the multiplexer is built from the validated
   `IOptions<DistributedCacheConfiguration>` with `ConfigurationOptions.Parse` and `AbortOnConnectFail = false`.
   `docs/Cache.md` and the installer's XML doc say that `abortConnect` is always `false`; the premortem
   `references/cache.md` gained the lesson "Redis connection factory change → `abortConnect` semantics at boot".
   **Test:** `ModuleInstallerTests.AddSolDistributedCache_RedisDownAtStart_FailsOpen` (connection string `localhost:1`
   with short timeouts and no `abortConnect=false`): `IRedisCache` falls through to the factory, the lock returns
   `null`, `TryAdd` returns `true`, and `HealthCheckService` reports `Unhealthy`. Before the fix it failed with
   `RedisConnectionException` when the lock was resolved. `ModuleResolutionTests` dropped its `abortConnect=false`.
1. **Minor — the two locks validated `expiry` differently.**
   **Finding:** the in-process lock accepted a zero or negative expiry and logged `TimeSpan.MaxValue` as a backend
   failure, while the Redis lock passed both to Redis.
   **Fix (`65398d8f`):** the internal `LockExpiry.Validate` runs first in both implementations:
   `ArgumentOutOfRangeException.ThrowIfLessThanOrEqual(expiry, TimeSpan.Zero)` and `ThrowIfGreaterThan(expiry, 365
   days)`. Decision for `TimeSpan.MaxValue`: rejected by the documented 365-day ceiling in both. The in-process method
   is not `async`, so it throws synchronously; the Redis one returns a faulted task; both surface on `await`. The
   interface XML doc, `docs/Cache.md`, and the core brief's release-notes input describe the rule.
   **Test:** `TryAcquireLock_ExpiryOutOfRange_Throws` in `LocalDistributedLockServiceTests` and
   `RedisDistributedLockServiceTests` (zero, −1 s, 365 days + 1 tick, `TimeSpan.MaxValue`): all eight cases failed
   before and pass; `TryAcquireLock_MaximumExpiry_Acquires` pins the 365-day boundary. The local log test gets its
   Warning from a substituted `TimeProvider` that throws.
1. **Minor — the Redis release logged "released" for a lock it no longer held.**
   **Finding:** `LockHandle.DisposeAsync` ignored the compare-and-delete result.
   **Fix (`967d7dd4`):** Debug `Lock released: [{LockKey}]` only when the script deleted the key, otherwise Warning
   `Lock [{LockKey}] expired before release`. The handle now releases once, because a second dispose would otherwise
   log that Warning.
   **Test:** `RedisLockReleaseTests.Dispose_AfterExpiryAndTakeover_WarnsAndKeepsNewHolder` (200 ms expiry, a second
   holder takes the key, the first handle is disposed: Warning, and the second holder's key remains) and
   `Dispose_Twice_ReleasesOnceWithoutWarning`; both failed before and pass.
1. **Cleanup — unreachable empty-key checks.**
   **Fix (`05877e5e`, `refactor(cache)`):** removed from `RedisCache` and `ScopedCache`; the key is JSON (a null key is
   `"null"`), so the check could not fire. No test or document referred to it.
