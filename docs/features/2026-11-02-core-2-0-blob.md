## Deviations

### Recreation after deletion happens in the write path (step 01)

**Original plan:** a `ContainerNotFound` (404) on use evicts the factory's cache entry and creates the container
again once; only the two `Connection/` files change.

**Actual implementation:** `WriteToBlob` catches `RequestFailedException` with `BlobErrorCode.ContainerNotFound`,
calls `CreateIfNotExistsAsync` on the same client, and retries the upload once. The extensions never see the factory,
and the cached `BlobContainerClient` is a stateless handle, so recreating the container through it is enough; the
factory evicts an entry only when its creation failed, so a transient failure is not cached forever. Reads do not
recreate: after a deletion the blob cannot exist, so they still fail with 404. `GetConnection` stays synchronous (an
async accessor would change `IBlobConnectionFactory`), so the first call per name waits for `CreateIfNotExistsAsync`.

### Manual Azurite checks instead of automated tests (steps 01, 02, code review)

**Original plan:** no automated test (Q6, AR-1); a manual Azurite check is recommended in each PR; DreamTravel usings
change if it uses Blob.

**Actual implementation:** no test project or sample references `SolTechnology.Core.Blob` or `Blob.Testing`, so no
using changed and the coverage gap stays AR-1. Uncommitted consoles under `.scratch/` ran against Azurite through
`AddSolBlob`. Step 01: the 1.x factory copied verbatim threw on 49 of 50 parallel first calls (19 of 50 in the
2026-11-06 rerun); the new factory returned one cached client, and a write after `AzuriteFixture.ClearAsync` recreated
the container and read back. Step 02: JSON and Avro round-trips with the format key present right after the upload,
the one-argument overload writes `json`, a custom `owner` key survives an Avro overwrite (RM-12), a blob written the
1.x way and a blob without the key both read back, and a cancelled token stops both `WriteToBlob` and `ReadFromBlob`.
Steps 01, 02, and 04 had to run these checks on `azurite:latest`, because the fixture's default image rejected the SDK; the
code review fixed the default, and the final run used it.

### `docs/Blob.md` rewritten to the canonical structure (step 04)

**Original plan:** fix the stale names at `:15-23,43`, add `using SolTechnology.Core.Blob;` and `CancellationToken`.

**Actual implementation:** the page was rewritten to the `PublicDocumentationGuide.md` structure (lead, Features,
Registration, Configuration, Usage, Testing, Conventions); the `Overview` heading, the auto-binding claim, and
`CreateConnection` are gone. The three C# blocks were copied verbatim into an uncommitted project that references
`Blob` and `Blob.Testing`; the registration block needed only `using SolTechnology.Core.Blob;` and
`WebApplication.CreateBuilder` in front. The build had 0 errors and 0 warnings, so no snippet is marked illustrative.
The Testing snippet compiled but failed at runtime on `azurite:3.35.0` until code review finding 1.

### `ReadFromBlob<T>` stays a classic extension method (step 05)

**Original plan:** convert every extension method to an `extension` block.

**Actual implementation:** `ModuleInstaller` and the non-generic Blob extensions use `extension` blocks; `ReadFromBlob<T>`
stays a classic `this` method, because for an unconstrained generic member of an `extension` block the SDK 10.0.100
compiler drops `T`'s nullable annotation on the emitted static method (CS8714 at static-form call sites). The exception
is recorded in Coding Guide §9.7. ApiCompat (both directions) showed only the compiler-generated `extension` marker
types.

### The Azurite bump landed here, not in testing-kits (code review)

**Original plan:** steps 01 and 04 left the fixture's default image as a follow-up for the testing-kits feature.

**Actual implementation:** the code review rated it Major, because the documented fixture could not run a single Blob
request, so this feature pinned `azurite:3.37.0` and the testing-kits brief records the pin.

Decisions taken without asking, as the user asked on 2026-11-06:

- Finding 1 pins a released image instead of passing `--skipApiVersionCheck`: 3.37.0 supports `2026-06-06`, and
  skipping the check would hide the next mismatch.
